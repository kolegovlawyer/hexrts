## [Дата: 2024-12-XX] - ИСПРАВЛЕНИЕ: Система координат тумана войны

### 🔧 КРИТИЧЕСКОЕ ИСПРАВЛЕНИЕ: Области видимости больше не смещаются при движении камеры

#### ❌ Обнаруженная проблема
- **Области видимости юнитов смещались** при движении камеры
- **Экранные координаты юнитов менялись** относительно камеры (649.94 → 658.27)
- **Неправильная архитектура:** Преобразование мировых координат в экранные относительно камеры

#### ✅ Решение - возврат к мировым координатам с правильным преобразованием
**Архитектурное изменение:**
- **GDScript (менеджер):** Передает в шейдер МИРОВЫЕ координаты юнитов (без преобразования)
- **Шейдер:** Корректно преобразует UV → мировые координаты с учетом позиции и зума камеры  
- **Результат:** Области видимости статично привязаны к мировым координатам юнитов

**Изменения в коде:**
1. **`scripts/fog_of_war_manager.gd`:**
   - Удалена функция `_world_to_screen()` (причина проблемы)
   - Позиции юнитов передаются в мировых координатах
   - Передача `camera_position` и `camera_zoom` в шейдер
   
2. **`shaders/fog_of_war.gdshader`:**
   - Исправлена функция `uv_to_world()` с правильной формулой преобразования
   - Добавлены uniforms `camera_position` и `camera_zoom`
   - Вычисления видимости в мировых координатах
   
3. **Система обновления:**
   - `update_frequency = 0.0` для обновления каждый фрейм
   - Сигналы камеры для мгновенного отклика на движение

#### 🛠️ Техническая информация
- **Система координат:** Мировые координаты (статичные, не зависят от камеры)
- **Производительность:** Без изменений, те же 60 FPS при 100+ юнитов
- **Совместимость:** Обратная совместимость с существующими картами

### 📡 ИСПРАВЛЕНИЕ: Синхронизация камеры с туманом войны

#### ❌ Обнаруженная проблема
- **Рассинхронизация**: Камера двигалась каждый фрейм, а туман обновлялся с задержкой (60 FPS)
- **Задержка отклика**: Области видимости "отставали" от движения камеры
- **Визуальное дерганье**: Туман смещался при движении камеры, затем возвращался на место

#### ✅ Решение - система сигналов реального времени
**Мгновенное обновление тумана:**
- **update_frequency = 0.0**: Туман обновляется каждый фрейм без задержки
- **Сигналы камеры**: `camera_moved()` и `camera_zoomed()` для мгновенного отклика
- **Оптимизация**: Сигналы отправляются только при реальном изменении позиции/зума

**Изменения в коде:**
1. **`scripts/camera_controller.gd`:**
   - Добавлены сигналы `camera_moved()` и `camera_zoomed()`
   - Отслеживание изменений позиции и зума для оптимизации
   
2. **`scripts/fog_of_war_manager.gd`:**
   - `update_frequency = 0.0` для обновления каждый фрейм
   - Функция `force_immediate_update()` для мгновенного обновления
   
3. **`scripts/map_fog_initializer.gd`:**
   - Автоматическое подключение сигналов камеры
   - Обработчики `_on_camera_moved()` и `_on_camera_zoomed()`

#### 🎯 Результат
- **Идеальная синхронизация**: Туман мгновенно следует за камерой
- **Плавная работа**: Никаких задержек или смещений областей видимости
- **Оптимизированная производительность**: Обновления только при реальных изменениях

### 🛣️ ИСПРАВЛЕНИЕ: Прямые пути движения юнитов

#### ❌ Обнаруженная проблема
- **Юниты двигались по кривым линиям** вместо кратчайших путей

**Изменения в коде:**
1. **`scripts/base_unit.gd`:**
   - Объединены функции `_process_move_order_immediate()` и `_process_move_order_heavy_bot()`
   - Упрощена логика обработки приказов
   - Убраны сложные алгоритмы обхода препятствий

#### 🎯 Результат
- **Прямые пути:** Юниты идут по кратчайшим маршрутам
- **Стабильная производительность:** Те же 60 FPS при 100+ юнитов
- **Упрощенный код:** Меньше сложности, больше надежности

  - Отладочные дисплеи и логирование

#### ✅ Революционное решение: FrameGroup распределенные вычисления

### 🔧 Техническая архитектура

#### 📊 Система FrameGroup (существующая оптимизация)
- **`FrameGroup.gd`** - распределение юнитов по группам

- **Принцип работы**: каждый фрейм обрабатывается только одна группа юнитов
- **Результат**: нагрузка распределена по 60 фреймам (при 60 FPS)

#### 🎯 Новая архитектура `_physics_process`

**РАНЬШЕ (все каждый фрейм):**

### 🐛 КРИТИЧЕСКИЕ ИСПРАВЛЕНИЯ: Ошибки сервера и видимости ботов (v1.2)

#### ❌ Проблема 1: Ошибка типизации в системе ботов
```
Invalid type in function '_order_hex_capture' in base 'Node (Bot)'. 
The Object-derived class of argument 1 (CharacterBody2D (BaseUnit)) is not a subclass of the expected argument class.
```

**Причина**: Функция `_order_hex_capture` ожидала `CommandUnit`, но получала `BaseUnit` в функциях:
- `_call_reinforcements_to_hex()` - подкрепления могут быть обычными юнитами
- `_coordinate_group_attack()` - групповые атаки включают все типы юнитов

**Решение**: Изменена типизация функции с `CommandUnit` на `BaseUnit`:
```gdscript
# БЫЛО:
func _order_hex_capture(command_unit: CommandUnit, hex_position: Vector2i)

# СТАЛО:
func _order_hex_capture(unit: BaseUnit, hex_position: Vector2i)
```

#### ❌ Проблема 2: Боты видны противникам при подключении по сети
**Причина**: Неправильный порядок инициализации видимости:
1. При создании юнита бота вызывается `owner_id` setter
2. Setter вызывает `update_visibility()` когда бот еще не добавлен в `TeamHandler`
3. Юнит скрывается от всех игроков
4. В `_ready()` `owner_team` инициализируется правильно, но `update_visibility()` больше НЕ ВЫЗЫВАЕТСЯ

**Решение**: Добавлена функция `_fix_visibility_after_init()`:
- Вызывается через `call_deferred()` после полной инициализации
- Принудительно обновляет видимость, игнорируя кэш
- Содержит специальную диагностику для ботов

**Новые функции**:
- `_fix_visibility_after_init()` - исправление видимости после инициализации
- Улучшенная диагностика в `update_visibility()` для ботов

- ✅ **Сервер больше не падает** от ошибок типизации в системе ботов

### 🐛 ИСПРАВЛЕНИЕ: Ошибка is_inside_tree при спавне ботов (v1.3)

#### ❌ Проблема: Критическая ошибка на сервере
```
E 0:34:03:807   base_unit.gd:43 @ @owner_id_setter(): Condition "!is_inside_tree()" is true. Returning: false
  <C++ Source>  scene/main/node.cpp:754 @ is_multiplayer_authority()
  <Stack Trace> base_unit.gd:43 @ @owner_id_setter()
                spawner_synchronizer.gd:26 @ custom_spawner()
                unit_spawner.gd:93 @ _internal_spawn_unit()
                base_fob.gd:185 @ _on_spawn_timer_timeout()
```

**Причина**: `owner_id` setter вызывался при создании юнита **ДО** добавления в дерево сцены, но внутри setter'а вызывался `is_multiplayer_authority()`, который требует `is_inside_tree() == true`.

**Цепочка проблемы**:
1. `base_fob.gd` → `_on_spawn_timer_timeout()` 
2. `unit_spawner.gd` → `_internal_spawn_unit()`
3. `spawner_synchronizer.gd` → `custom_spawner()` → устанавливает `owner_id`
4. `base_unit.gd` → `@owner_id_setter()` → `is_multiplayer_authority()` → **ОШИБКА**

#### ✅ Решение: Отложенная инициализация команды

**Новая архитектура setter'а**:
```gdscript
@export var owner_id : int = 1:
	set(value):
		owner_id = value
		
		# ИСПРАВЛЕНИЕ: Проверяем что юнит в дереве
		if not is_inside_tree():
			# Отложим инициализацию команды до _ready()
			_pending_team_initialization = true
			return
		
		# Если в дереве - инициализируем сразу
		if is_multiplayer_authority():
			_initialize_team_and_visibility()
```

**Новые компоненты**:
- **`_pending_team_initialization`** - флаг отложенной инициализации
- **`_initialize_team_and_visibility()`** - централизованная функция инициализации команды
- **Проверка в `_ready()`** - выполнение отложенной инициализации

**Улучшенная логика `_ready()`**:
```gdscript
# Выполняем отложенную инициализацию команды если нужно
if _pending_team_initialization:
	_pending_team_initialization = false
	_initialize_team_and_visibility()

# Инициализируем команду если не было отложенной инициализации
if owner_id != 1 and owner_team == null:
	_initialize_team_and_visibility()
```

- ✅ **Ошибка is_inside_tree устранена** - сервер больше не падает при спавне ботов

- ✅ **Надежность** - двойная проверка инициализации команды

### 📋 Алгоритмы ИИ

#### Стратегическое планирование
1. **Расширение** (`expand`) - захват нейтральных гексов
2. **Оборона** (`defend`) - группировка юнитов для защиты контролируемых гексов  
3. **Атака** (`attack`) - координированные атаки на вражеские позиции

#### Тактические решения
- **Оценка угрозы** - анализ соотношения вражеских и союзных юнитов
- **Контроль территории** - подсчет контролируемых гексов
- **Управление ресурсами** - автоматический спавн юнитов при достаточных очках

### 🎯 Особенности реализации

#### Архитектурные принципы
- **Неинвазивность** - система ботов не изменяет существующий игровой код
- **Модульность** - боты представлены отдельным классом с четким интерфейсом
- **Производительность** - принятие решений каждые 2 секунды, проверка спавна каждую секунду
- **Масштабируемость** - поддержка множественных ботов на сервере

#### Интеграция с игровыми системами
- **Система очков** - боты используют существующую валидацию спавна через `GameManager`
- **Система команд** - полная интеграция с `TeamSystem` и `PlayerProfile`
- **FOB система** - боты используют существующую очередь спавна через `base_fob.gd`
- **Сетевая архитектура** - боты работают как специальные клиенты

### 🚀 Использование

#### Создание бота (на сервере)
1. Запустить Host (создать сервер)
2. В левом нижнем углу появится панель "🤖 Управление ботами"
3. Выбрать команду (Team A/B)
4. Нажать "➕ Добавить бота"
5. Бот создается мгновенно и начинает играть

#### Управление ботами
- **Добавление**: кнопка "➕ Добавить бота" в серверном UI
- **Удаление**: кнопка "❌" рядом с каждым ботом в списке
- **Мониторинг**: список показывает юнитов каждого бота в реальном времени

#### Поведение в игре
- Бот автоматически спавнит первый командный юнит
- Начинает захватывать ближайшие нейтральные гексы
- При атаке вызывает подкрепления
- Адаптирует стратегию под ситуацию

### 🐛 Известные ограничения
